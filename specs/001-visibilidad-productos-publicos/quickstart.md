# Verificación manual reproducible

Este documento describe verificaciones para la implementación futura; no certifica que hoy pasen. No hay script `test`, lint ni build en `backend/package.json`. El script existente `backend/scripts/bulk-upload-imagenes.js` sirve para cargas y no se usa aquí.

## Preparación segura

1. La persona responsable prepara el entorno contra una **base descartable**, como una rama aislada de Neon o PostgreSQL local; nunca contra producción. Verifica por un medio autorizado la rama Git de `backend/`, el host de PostgreSQL y el destino de la API antes de crear o editar fixtures. El agente no lee ni escribe archivos `.env`.
2. Esa persona prepara IDs conocidos: `VISIBLE` (`activo=true`, `web=true`, variante activa con stock), `INACTIVO` (`activo=false`), `NO_WEB` (`activo=true`, `web=false`), `DESTACADO_INACTIVO`, `DESTACADO_VISIBLE`, `VARIANTE_INACTIVA`, un cliente de prueba sin fila `Carrito` y otro con carrito e ítems. En el carrito existente prepara además un `ItemCarrito` de `ProductoImprovisado` sin variante para comprobar `disponible: true`. También prepara credenciales de cliente y administrador del entorno descartable.
3. Iniciar el backend con el script existente `npm run dev` desde `backend/`; su puerto predeterminado es 3000. En otra terminal, iniciar `frontend/` con `npm run dev` si se verifica la presentación del carrito.
4. En una terminal PowerShell, definir solo parámetros de prueba, sin imprimir ni guardar tokens: `$apiBase='http://localhost:3000/api'`; `$clienteToken='<token-de-prueba>'`; `$adminToken='<token-admin-de-prueba>'`; `$visibleId='<id>'`; `$inactivoId='<id>'`; `$noWebId='<id>'`; `$varianteInactivaId='<id>'`; `$varianteNoWebId='<id>'`. Sustituir los marcadores por datos del entorno aislado.

## Casos

1. **Detalle de producto retirado.** Ejecutar `curl.exe -i "$apiBase/productos/$inactivoId"` y `curl.exe -i "$apiBase/productos/999999999"` con un ID inexistente confirmado. Ambos deben responder 404 y `Producto no encontrado`. Repetir con `$noWebId`.
2. **Destacados.** Ejecutar `curl.exe -i "$apiBase/catalogo-inicio"`. Los IDs de `DESTACADO_INACTIVO` y de un producto `web=false` no deben aparecer; `DESTACADO_VISIBLE` y los demás deben conservar su orden relativo. Consultar por ID cada selección oculta y esperar 404; consultar la visible y esperar 200.
3. **Agregado rechazado.** Para el cliente sin carrito, la persona responsable comprueba con una consulta de solo lectura en la base descartable que no existe una fila `Carrito` para su `usuarioId` (por ejemplo, `SELECT COUNT(*) FROM "Carrito" WHERE "usuarioId" = <id>;`). No ejecutar antes `GET /carrito`: esa ruta crea el carrito si falta. Ejecutar `curl.exe -i -X POST "$apiBase/carrito/items" -H "Authorization: Bearer $clienteToken" -H 'Content-Type: application/json' --data '{"talleProductoId":123,"cantidad":1}'`, sustituyendo `123` por la variante del producto inactivo. Esperar 400 y mensaje español de variante no disponible; repetir con `$varianteNoWebId` y `$varianteInactivaId`. Repetir con una variante activa de producto visible, pero solicitando una cantidad superior a su stock; esperar 400 `Stock insuficiente`. Después de cada rechazo, comprobar por consulta de solo lectura que sigue sin fila `Carrito`. Por separado, para el cliente con carrito existente, registrar `GET /carrito` antes y después de cada POST rechazado y comprobar los mismos ítems, cantidades y subtotal.
4. **Producto vigente.** `GET /productos` y `GET /productos/$visibleId` deben incluir el producto visible; `GET /catalogo-inicio` debe conservarlo si está seleccionado. Agregar su variante con el mismo POST del caso 3, usando su ID, y esperar respuesta exitosa con el ítem actualizado. En el detalle, las variantes sin stock no deben aparecer.
5. **Administrador.** Ejecutar `curl.exe -i "$apiBase/productos?admin=true" -H "Authorization: Bearer $adminToken"` y comprobar que incluye productos inactivos y `web=false`. La edición administrativa existente debe seguir funcionando en el entorno aislado; realizarla solo sobre fixtures de prueba y restaurar su estado después.
6. **Ítem ya presente cuando se retira el producto.** Agregar una variante visible al carrito de prueba. Desactivar el producto fixture mediante el flujo administrativo existente. `GET /carrito` debe conservar el ítem, cantidad, `precioUnitario` y subtotal, con `disponible=false`. Pedir por PUT una cantidad mayor que `item.cantidad`: 400 sin cambios. Pedir una cantidad menor: debe aceptarse si la variante sigue activa y la cantidad cabe en stock; la respuesta debe incluir `disponible=false`. Si la variante es `inactivo` o la cantidad supera stock, debe conservarse el rechazo anterior. `DELETE /carrito/items/:id` debe seguir permitiendo quitarlo. Abrir `/carrito` en frontend y comprobar la marca visible “No disponible” y el aumento deshabilitado.

En los casos 3, 4 y 6, comprobar que `GET /carrito`, POST/PUT/DELETE de ítems y DELETE `/carrito` devuelven `disponible` en cada ítem restante; un `ProductoImprovisado` sin variante devuelve `true`. El subtotal debe seguir incluyendo ítems no disponibles. Estas comprobaciones usan solo fixtures descartables.

## Cierre

Revisar los casos contra `spec.md` y `contracts/catalogo-carrito.md`; anotar resultados reales, entorno descartable usado y cualquier caso no ejecutado en `verificacion.md`. Restaurar únicamente los fixtures creados para esta verificación.
